# 知识门户、文档导入与多源接入：分阶段设计

状态：原分阶段设计与当前交付对照。更新日期：2026-09-20。日常操作以[知识库使用与流转](知识库使用与流转.md)为准，配置以[门户说明](../portal/README.md)为准。

本设计在现有 Markdown、Obsidian、GBrain 和审核入库流程上增加可选能力。先支持个人本机使用，团队协作后置；首版不做应用登录和权限管理。下方阶段保留设计边界，不能把暂停或未来规划当作已实现功能。

## 当前交付对照

| 阶段 | 当前状态 |
|---|---|
| P1—P3 浏览、图谱、搜索 | 已实现；文字导航、窄屏目录及页内切换已补齐 |
| P4 Markdown / 审核 | 已实现；网页支持逐条选择、预览和确认本地保存，Git 发布在网页外 |
| P5 DOCX / 文字 PDF | 已实现本地解析、原件及附件保留；复杂版式须核对 |
| P6 扫描 PDF / 图片识别 | 暂停，未实现 OCR |
| P7 模型执行 | 已改用 Codex / DeepSeek Harness；原模型 API 渠道废弃，缺失只提示 |
| P8 来源 | IMA 知识库/笔记及手动更新已实现；语雀单篇代码已实现、真实账号验收暂缓；钉钉暂停 |
| 导入后的知识候选 | 后端自动提炼，有限旧知识对照，用户确认后保留在资源资料卡 |

不新增网页同步按钮，不自动改写主题 Wiki，不把用户实例的源码/凭据/知识正文打包为通用安装模板。

本文只记录通用设计。知识正文保存在使用者自己的知识目录，私有仓库、服务器地址、凭据、运行状态和验证报告保存在实例记录中，不上传到 EvoKBase。

## 目标与不变边界

新增四类能力：

1. 网页浏览目录、正文、附件和真实链接关系图，接入已有搜索。
2. 从网页上传 Markdown、Word、PDF、图片，解析后审核入库。
3. 按需读取腾讯 IMA、语雀、钉钉文档等外部来源，逐个平台实现。
4. 已审核知识推送到指定 GitHub 私有仓库后，由专用 runner 自动刷新索引。

原有规则继续成立：

- Markdown 是知识正文的事实源，GBrain 保存可重建的检索索引。
- 网页与 Obsidian 读取同一份知识，不建立网页专属正文副本。
- 原件归档、全文转换与知识提炼分开；解析成功不代表内容已获批准。
- 原审核、精确提交和真实检索验收保留。发布通道在 P9 明确切换，其他阶段不绕过旧流程。
- 停止新应用后，旧编辑、检索和入库入口仍可使用；已确认发布的文档不会随网页停止而撤回。
- 不依赖 WeKnora 运行服务。文档解析可参考其流程，使用成熟解析库，具体依赖在实施时核实。

## 模块与调用方向

先实现一个本机网页应用，前端配本机后端，模块从普通函数开始，不预建微服务、插件平台或通用工作流引擎。

```text
网页浏览、图谱 → 只读文件模块 → 现有 Markdown 和附件
网页搜索      → GBrain 接入  → 现有检索索引

本地上传 / 外部来源读取
        ↓
独立暂存 → 必要的格式解析 / 图片识别 → 预览草稿
                                           ↓
                                   原审核与用户确认
                                           ↓
                                 正式资料、知识文件
                                           ↓
                                  精确 Git 提交、推送
                                           ↓
                           GitHub 私有仓库发布分支
                                           ↓
                          专用 runner → 固定刷新脚本
                                           ↓
                              同步、向量化、检索验收
```

| 模块 | 输出 | 不承担的职责 |
|---|---|---|
| 文件读取 | 目录、正文、元数据、附件及链接 | 不修改正文、不操作 Git、不调用模型 |
| 关系图 | 由真实引用得到的节点、边和反向链接 | 不推测关系、不将缓存写回知识 |
| 搜索接入 | 既有 GBrain 命中片段和来源 | 不新增向量库、不重写检索策略 |
| 来源接入 | 选定远端文档的正文或文件、附件、来源 | 不审核、不发布、不向来源平台写回 |
| 文档解析 | Markdown、附件、来源位置和缺失警告 | 不提交 Git、不直接写 GBrain |
| 本地 Harness 调用 | 本篇资料的要点候选与有限旧知识比较 | 不执行 OCR、不决定知识批准、不自动发布 |
| 导入发布 | 已审核文件的精确提交和刷新回执 | 不自动批准、不混入其他修改 |

依赖只从新模块指向既有文件和接口，旧系统不依赖新网页。新增第二个真实来源或模型渠道后，再提炼必要的共用接口。

## 数据存在哪里

| 数据 | 存储边界 |
|---|---|
| 未审核文件、解析草稿 | 应用独立暂存目录，位于正式知识库之外，不进入正式索引 |
| 确认保留的原件、来源快照、资料卡 | 知识库资源层；原件不可覆盖，新版本保留来源关系 |
| 解析正文与附件 | 对应资料目录，正文使用 Markdown，附件使用稳定相对引用 |
| 提炼并批准的知识 | 按现有规则进入主题、项目等目录 |
| 来源映射、任务进度、缓存、日志 | 应用独立运行目录，不当作知识正文 |
| 已发布的知识版本 | 使用者指定的 GitHub 私有仓库；与公开 EvoKBase 分开 |
| 检索索引与向量 | 既有 GBrain 服务 |

具体目录在实例基线中确定。原件和大附件是否纳入 Git，以及哪些历史允许首次推送，必须在发布前明确；`.gitignore` 不会移除已跟踪文件或历史中的内容。

在线平台不一定提供可下载的原文件。只对实际获得的正文、附件和来源信息建立快照，不把搜索片段冒充完整原文。远端原文继续保留在原平台，本地批准知识仍由本地规则维护。

最少记录：文档相对路径及内容摘要；解析器版本、原文位置和警告；审核对应的内容版本；本轮精确文件清单；Git 提交与刷新状态。原件或草稿修改后，旧确认失效。

## 实施顺序

阶段编号用于追踪，不表示所有阶段必须串行。建议先完成 P0 的发布基线，再实施 P9；随后推进 P1，逐步增加图谱、搜索和导入。

| 阶段 | 交付 | 前置条件 | 核心验收 |
|---|---|---|---|
| P0 | 边界、环境基线和小样本 | 无 | 实例与公开材料分开，旧流程和恢复入口可定位 |
| P9 | GitHub 私有库 push 自动刷新 | P0 发布基线、现有刷新能力 | 推送触发、权限限制、失败重试和真实召回通过 |
| P1 | 只读网页浏览 | P0 浏览基线 | 同一份 Markdown，服务离线仍能浏览 |
| P2 | 链接图与反向链接 | P1 文件模块 | 每条关系可回原文，不猜测歧义目标 |
| P3 | 网页搜索 | P1、既有 GBrain | 结果与原文正确映射，离线不阻塞浏览 |
| P4 | Markdown 导入完整流程 | P1、原审核及选定发布通道 | 暂存、确认、精确发布、恢复和召回通过 |
| P5 | DOCX、文字 PDF | P4 | 正文、表格、附件与原件核对，部分失败可见 |
| P6 | 扫描 PDF、图片识别 | P5、可用识别后端 | 逐页核对，未处理内容不冒充完整结果 |
| P7 | 本地 Codex / DeepSeek Harness | 已安装工具及实际调用需求 | 缺失提示、取消、超时和候选流程；API 渠道不再保留 |
| P8 | IMA、语雀、钉钉等来源 | P4；按返回格式使用 P5/P6 | 逐平台验收来源完整性、去重、更新冲突 |

P2、P3 不作为 P4 的代码前置条件。P8 不依赖 P7；能取得正文时可在 P4 后实施。每次只交付一个阶段或一个小任务，验证后继续。

### P0：基线与准备

1. 明确知识根目录、网页展示范围、附件位置、检索排除项和新应用运行目录。
2. 记录已有 Git 分支、发布入口、GBrain 接入方式与凭据引用，不复制密钥正文。
3. 准备隔离样本：中文路径、重名文件、链接别名和锚点、表格、附件及各类文档；不向生产库写测试知识。
4. 按下一阶段确定技术栈和代码位置。先做 P9 时先完成发布相关基线；浏览样本等在 P1 前补齐，不将部分准备记为全部 P0 完成。

### P9：GitHub 发布与固定刷新入口

已确定采用 GitHub Actions 自托管 runner，即在使用者环境中接收任务并执行的程序。工作流只执行知识库刷新，不采用定时拉取方案。

1. 确认私有仓库、发布分支、文件及历史上传范围。核对服务器出站连接、操作系统和运行账户；网络测试通过不等于私有仓库认证或真实工作流通过。
2. 仅指定发布分支的 push 触发生产刷新。本地 commit、其他分支、标签和外部 PR 不触发；允许手动重跑已发布版本以恢复失败。
3. 工作流调用服务器受保护的固定脚本：校验仓库、分支和提交，取得发布版本，执行既有 sync/embed、状态及真实检索验收，记录回执。不接收任意命令或脚本路径，不执行知识仓库随提交携带的脚本。
4. runner 使用专用低权限账号，不授予通用管理员权限或 Docker socket 访问。固定脚本和可执行依赖不能被 runner 或知识库 Git 更新改写；只开放刷新必要的目录、服务和凭据。流程文件变更需受控审阅。固定一行命令不是权限隔离，必须验证越权拒绝和正常刷新。
5. 自动、手动刷新共用串行边界，记录触发提交、实际处理提交和最后成功提交。过期任务不能使服务退回旧版本；连续推送最终追上最新发布版本，不承诺每个中间版本都单独完成。
6. 区分推送成功和刷新成功。失败可对同一版本重试，不制造重复提交；索引部分更新失败时明确标记不完整，不宣称自动原子回滚。
7. 先验证隔离样本，再切换真实发布。新旧 Git 通道不同时作为自动发布源；恢复旧通道前暂停自动任务并核对版本，服务器脏工作区或历史分叉时停止，不强制覆盖。

停用 runner 后，已有正文和索引继续可用，自动刷新停止；故障恢复仍使用受控的同版本刷新入口。该阶段不依赖网页启动。

### P1—P3：只读入口

- P1：目录树、Markdown/frontmatter、附件、WikiLink 和相对链接。约束文件读取范围、过滤危险 HTML；本机版绑定回环地址，不因暂不做登录而开放到公网。Obsidian 修改后网页刷新可看到最新内容。
- P2：复用 P1 链接解析，先做当前文档一跳关系和反向链接，再做全库视图。代码块示例不作为关系；重名、失效链接明确标记；frontmatter 只解析明确文档引用，缓存可重建。首版不依赖未验证的 GBrain 图谱接口。
- P3：服务端调用已有 GBrain 检索，显示来源、片段与打开原文入口。区分已发布索引与本地未发布正文；不在本阶段新增聊天或排序算法。检索故障不影响浏览。

### P4：先用 Markdown 跑通入库

1. 上传到独立暂存目录，预览正文、来源、目标路径和拟新增文件，不自动覆盖同名资料。
2. 接入原审核与用户确认。若已有评审角色尚无网页 API，先通过原 Agent 入口完成交接；网页状态标记不能代替真实评审。
3. 对确认版本精确提交，检查其他暂存内容、未提交知识及整段待推送提交。P9 启用后统一推送并获取回执，不额外触发旧发布链路。
4. 串行发布，记录阶段回执。解析尽量在正式写入前完成；写入后失败只恢复本任务拥有且未被后续修改的文件，不使用全库 reset/stash。

验收必须覆盖拒绝或待审内容未入索引、其他修改不混入、重试不重复发布、失败恢复后旧入口可用。停止网页不会撤销已经发布的文件。

### P5—P7：文件格式与模型渠道

- P5：先支持 DOCX 和文字 PDF，老式 DOC 单独验证。使用成熟解析库输出正文、附件和能确认的位置；无法确认页码不编造。混合 PDF 中的扫描页标记需要识别，不以部分提取代表全文成功。预览与正式浏览复用附件引用规则。
- P6：只选一个实际可用 OCR/视觉后端，优先在支持范围复用已有配置。纯文字解析不依赖视觉模型；识字结果与模型描述分开，保留原图和对应页码。缺少配置或识别失败不影响浏览及文本导入。
- P7：真实需要第二个渠道时再提炼共同调用约定。Codex、DeepSeek Harness 等分别核实自身认证、文本/图片能力、输出、超时和取消；不默认等于通用 HTTP API。执行只获得必要暂存材料，输出仍是候选，不承担发布职责。

### P8：逐个平台接入外部资料

1. 分别核查 IMA、语雀、钉钉的认证、正文或原文件、附件、目录、分页及版本能力；有技能或搜索接口不等于能导出完整文档。
2. 先选择一个平台，手动选择文档并导入暂存区；取得正文就转换，取得文件就复用解析器。接口不能提供全文时明确限制，可用平台导出文件再上传。
3. 其余平台逐个作为独立任务交付。IMA 笔记与知识库文件、钉钉在线文档与云盘文件分别核实，不按同一对象臆测接口。
4. 来源身份包含平台、账号/空间与远端文档标识，同时保存原文链接、获取时间、可用版本及内容摘要。不能只按标题去重；附件获取不完整、临时链接和分页中断必须可见。
5. 后续增加手动检查更新：无变化不重复发布，有变化生成差异候选，本地编辑冲突显式呈现，不覆盖已整理知识。远端删除与权限失效区分，不自动删除本地文件，不双向写回。
6. 确实需要持续更新后再单独增加定时读取或平台事件接入，最多生成待审候选，仍不自动批准知识。

停用某个平台只影响该来源的新读取，已批准 Markdown 和其他导入入口继续可用。

## 凭据与准备事项

| 用途 | 何时准备 |
|---|---|
| 目录、关系图、MD/DOCX/文字 PDF 解析 | 无需模型 Key |
| 既有 GBrain 检索和向量化 | 复用既有服务配置，不把 Key 交给浏览器 |
| 图片或扫描件识别 | P6 核实已有渠道能力，不默认现有 Key 支持视觉模型 |
| 外部资料平台 | P8 配置对应读取凭据或会话，与模型 Key 分开 |
| GitHub 私有仓库 | P9 确定目标及必要访问权限，凭据不写进正文、仓库或日志 |

应用没有登录不代表外部平台无需认证。读取资料的权限与交给模型处理的范围分别核对。用户不需要在最初一次性准备所有平台账号或模型配置。

开始 P9 前只需确定：私有仓库归属与名称、拟上传内容及历史范围、可完成执行器注册和专用账号配置的访问条件。能由现有工具完成的操作无需用户手动重复执行；只有登录、权限不足等具体阻碍出现时才请求必要协助。

## 验证与当前状态

每阶段只运行相关检查：页面与链接改动不触发生产索引重建；新增解析器对照原件并做少量导入验证；发布通道变更验证权限、版本、失败恢复与真实召回。已有检查通过后不因计划文档更新重跑业务测试。

当前仓库新增的是设计文档和阅读入口。P0 的实例基线、P9 网络探测等实际结果由使用者保存为实例记录；本仓库不以单个实例的检查代表其他环境已经验收。P1—P9 的功能、工作流和部署均尚未由本设计交付。

P9 技术依据：[GitHub push 事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push)、[自托管 runner 通信要求](https://docs.github.com/en/actions/reference/runners/self-hosted-runners)、[工作流安全](https://docs.github.com/en/actions/reference/security/secure-use)、[并发语义](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)。具体配置在实施时按官方说明与真实环境核对。
