# EvoKBase

以 Markdown 为事实源、由真实任务与反馈驱动、经人工审核持续更新的自进化知识库。项目提供个人知识工作台，以及可交给 AI 执行的团队搭建与使用手册。

从零建立 Markdown 知识库，用 Obsidian 或本地网页阅读，通过 GBrain MCP 检索。知识输入有三条路径：**对话中的子 Agent、本地文件、第三方数据源**。它们把任务经验和外部资料汇入同一份知识文件，再供后续任务使用。Horizon 是可选的外部资料发现工具。

团队共同维护知识内容，成员使用各自的 Agent 查询和提出候选，由约定的知识维护者审核正式入库。手册先覆盖成员本机运行的方式，共享范围和审核约定由团队明确。

自动知识流程只用于业务分析、业务开发或明确要求查询知识库的任务。普通问答、聊天、文档润色和非业务配置维护跳过两个子 Agent；“继续”沿用任务范围，已有查询覆盖且范围未变时复用结果。

## 为什么要搭建

长期工作中，值得留下的内容经常散在聊天记录、本地文档和第三方平台里：解决过的问题再次从头排查，换个对话就要重讲项目背景，收藏了很多资料却很少用于实际决策。即使保存了最终答案，也容易丢掉“为什么这样选、哪些方法试过无效、什么条件下才适用”。

EvoKBase 希望把这些内容整理成可以被下一次任务读取、核对和复用的知识。搭建它的目的，是让一次工作的成果继续帮助后续工作，并让过时或错误的经验有机会被纠正。

它适合持续处理同一领域或项目、需要复用历史决策与排障经验，并愿意审核知识的个人和团队。如果需求只是临时对几份文档提问，文档问答工具通常更省事；如果只需要维护一份阅读或研究 Wiki，也可以从较轻的 LLM Wiki 工作流开始。

## 能带来什么好处

| 希望改善的问题 | 本项目提供的机制 | 收益成立的前提 |
|---|---|---|
| 同类问题反复研究 | 将验证过的决策、步骤和适用边界沉淀为可检索知识 | 后续任务确实读取并采用，减少重复调查 |
| 新对话缺少项目背景 | 项目知识独立于聊天保存，按任务范围查询 | 相关内容已审核、纳入索引并被正确召回 |
| 资料分散、收藏后难以利用 | 对话、本地文件、第三方资料汇入同一知识目录 | 选择有价值的内容，持续整理而非只增加文件 |
| AI 总结混入猜测或失效结论 | 保留原件与来源，区分候选、正式正文和待验证项 | 人工核对证据；有引用不等于结论一定正确 |
| 知识难以迁移、修改难以追溯 | Markdown 可直接阅读，Git 记录已提交变化，检索索引可重建 | 正文与附件有备份，私有配置和暂存数据另行保管 |

这些是当前机制支持的预期收益，还没有对照评测证明本项目比其他方案检索更准、回答更好或成本更低。衡量搭建是否值得，应记录知识被再次采用的情况、减少的重复调查，以及同类错误是否更少重现。

## 三条知识进入路径

| 路径 | 内容从哪里来 | 怎么处理 | 确认后保存什么 |
|---|---|---|---|
| 对话子 Agent | 真实任务中的问题、决策、解决方案和已验证经验 | 查询角色先读相关旧知识；任务完成且有经验线索时，评审角色给一条简短候选；用户选中后起草正文 | 用户确认的知识正文或修改差异，写入对应主题、项目等目标文件 |
| 本地文件 | 用户上传的 Markdown、DOCX、文字 PDF | 门户暂存原件；可调用本地 Harness（AI 助手执行程序）提炼要点、有限对照旧知识；用户核对并选择内容 | 资源目录中的原件、解析产物和资料卡；要点保存在资料卡中 |
| 第三方数据源 | IMA 知识库、个人知识、笔记，以及有读取权限的语雀单篇文档 | 用户选定资料后读取到暂存区，沿用门户的整理和审核流程 | 带来源的资源资料包；进一步沉淀为主题或项目知识时另行审核 |

三条路径使用两套执行方式：对话由 Codex 原生子 Agent 处理，本地文件和第三方资料由门户后端调用已选 Harness 处理。网页导入后即可触发整理，无需再到对话里发指令。第三方接入按当前支持范围逐篇读取，不自动搬空外部资料库。

资料进入资源目录后可供查阅；提炼为长期方法、纠正旧知识或修改工作规则，需要审核具体目标与正文。获准文件通过**知识库自己的 Git 仓库**提交、推送，并按实例配置更新检索索引。操作步骤见[知识库使用与流转](docs/知识库使用与流转.md)。

## 为什么叫“自进化知识库”

EvoKBase 把知识的输入、使用和改进连接成一个可重复的流程：**读取已有知识 → 完成真实任务 → 获得结果与反馈 → 核对增量和改进依据 → 人工批准更新 → 下一次任务采用并验证**。三条输入路径提供新材料，后面的反馈闭环决定这些材料能否改善未来工作。

进化体现在三个方面：

1. **知识持续更新。** 新证据可以补充旧结论、修正错误、明确适用边界；重复或没有价值的内容跳过，保留来源及变更历史。
2. **经验参与下一次工作。** 已确认的决策、排障步骤和案例被后续任务检索、读取和采用，减少重复调查，让经验跨任务复用。
3. **方法接受反馈检验。** 实际使用暴露缺口后，提出对应知识、模板或工作规则的具体修改；维护者批准后应用到同类任务，再比较行为和结果是否改善。

例如：导入一份排障资料后，在实际任务中发现它缺少一个适用条件；把复现证据与旧知识对照，提出补充该条件的候选，经确认后更新并发布。下次遇到同类问题时，Agent 读取新版本并据此调整排查顺序；有实际结果证明避免了原来的误判，才构成一次可验证的进化。这个例子说明验收方式，不代表项目已经完成该案例。

**“自”体现在已配置流程能主动检索、提炼和提示改进；更新权仍由人掌握。** 当前提供了资料接入、有限知识对照、候选审核、Git 版本管理衔接，以及反馈与进化的操作规范。反馈归纳、规则修订和效果验证仍需按手册组织执行；没有无人值守的全库改写或模型训练。新增文件、生成摘要、推送成功都不能单独证明进化有效，长期效果要由真实使用记录验证。具体方法见[操作手册第 08 章](docs/从零搭建操作手册.md#10-第-08-章受控反馈和自进化)。

## 与 RAG、LLM Wiki 有什么区别

三者处于不同层次，可以组合使用。**RAG（检索增强生成）是一种利用检索资料辅助模型生成回答的技术方法**；EvoKBase 的旧知识对照和任务查询也使用检索能力。这里对比的是以文档问答为主的 RAG 用法，不把所有 RAG 产品都视为只有上传和问答。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

这里的 **LLM Wiki 指 Karpathy 提出的原始工作模式**，不是某个同名产品：由模型持续整理有链接的 Markdown Wiki，保留原始资料，执行摄取、查询和质量检查。原文也包含人工参与、回答回存、规则调整与 Git，因此持久化和反馈并非 EvoKBase 独有。[LLM Wiki 原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

| 比较点 | 文档问答型 RAG | LLM Wiki 原始模式 | EvoKBase 当前做法 |
|---|---|---|---|
| 侧重点 | 检索依据并生成回答 | 持续整理相互关联的 Wiki | 让资料和任务经验经审核后参与后续工作 |
| 知识处理 | 检索相关内容供本次回答使用 | 摄取时综合资料并维护页面 | 门户保存资料包；对话筛选经验，选中后起草，再确认正文 |
| 更新组织 | 由应用设计文档更新与治理流程 | 由规则文档约定摄取和维护 | 具体角色、Hook 提示、暂存审核和知识私库 Git 发布衔接 |
| 检索方式 | 依实现使用关键词、向量或混合检索 | 索引文件起步，搜索工具可选 | 本地文件阅读与 GBrain 检索分开，核对来源和版本 |
| 本项目关注的验收 | 是否找到合适依据、回答是否可靠 | 页面关联与内容一致性维护 | 除来源和版本外，还要求用后续任务验证方法更新的效果 |

上表比较各自的侧重点，不是功能排他清单。RAG 应用同样可以加入 Agent、人工审核和持续评估；微软的 RAG 指南就覆盖了回答依据、完整性、正确性与 Agent 检索效率等评估维度。[RAG 评估指南](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase)

**EvoKBase 的具体价值在于把这些能力组织成一套面向实际工作的可执行流程：** 外部资料和任务经验有明确入口，候选先筛选再起草，正文经确认才进入目标文件，发布后核对索引，后续反馈再推动有依据的修改。它与 LLM Wiki 的持久化知识思路相近，额外明确了本项目的输入渠道、任务调度、审核步骤和反馈验收要求；这是一种实现与工作流程的取舍，不能据此宣称全面优于其他方案。

相应的成本也需要接受：审核和维护会占用时间，子 Agent 和模型调用会增加延迟与用量；当前对照范围有限，门户导入不会自动维护整套主题 Wiki；反馈效果评估仍需按手册执行。Markdown 本地保存、本地 Harness 调用也不意味着模型完全离线。当前更适合先在个人或小范围协作中验证价值，门户尚不提供多人登录和权限管理。

## 怎么用

**已经搭好，想直接使用：** 阅读[知识库使用与流转](docs/知识库使用与流转.md)，按“导入资料 → 选择要点 → 确认保存”操作。保存后本地立即可读；远程同步和搜索更新走独立知识仓库的 Git 发布流程。

**第一次搭建：** 按下面的提示词从零开始。门户是本机应用；团队成员可以维护同一受控知识仓库，但门户暂不提供多人登录或权限管理。

下载本仓库，在 Codex 中打开，然后发送：

```text
请按 docs/从零搭建操作手册.md，帮我们从零搭建团队自进化知识库。
先检查环境和缺失参数，说明需要的软件、安装位置和本次改动。
在已授权范围内直接按官方文档安装、配置并验证；不要另写安装器。
不使用 AGENTS.md 调度知识流程，不接管已有知识库。
Horizon 按需启用。安装和配置的实际值写入我的实例记录。
需要网页时配置本地门户、独立暂存目录和已安装的本地 Harness；不配置旧模型 API 渠道。
需要推送后自动更新索引时，按主手册的 Git 发布章节配置独立知识私库及刷新工作流。
```

如果还没选知识库目录或是否启用 Horizon，AI 会在相关步骤询问。已有授权不逐步重复确认；需要你操作的登录和原生信任审核，会给出具体说明。

## 仓库提供什么

| 材料 | 用途 |
|---|---|
| `docs/` | 操作步骤、可复制提示词、验证和维护说明 |
| `templates/knowledge-base/` | 五层知识库入口和八类空白模板 |
| `templates/codex/knowledge_retriever.md` | 查询子 Agent 的角色提示词 |
| `templates/codex/knowledge_reviewer.md` | 评审子 Agent 的角色提示词 |
| `templates/codex/knowledge-flow.mjs` | 日常运行的 Hook 处理器：注入调度要求，由主 Agent 启动子 Agent |
| `tests/hook.test.mjs` | 配套 Hook 的行为检查，运行 `node --test tests/hook.test.mjs` |
| `portal/` | 本机浏览、搜索、图谱、多源导入、Harness 整理、逐条审核保存和独立 Git 发布命令 |

手册本身无需安装，没有 `evokbase` 命令或公开 npm 安装包。可选网页单独按 `portal/README.md` 安装依赖并启动。Git、Obsidian、Codex、GBrain、Horizon 及其依赖由执行 AI 根据当前官方说明直接安装。Hook 是日常运行材料，不承担软件下载、安装或升级。

当前为早期手册草案，许可证待确定。用户知识、凭据、实例配置和运行报告保存在用户自己的目录，不属于本仓库。旧安装器试验已退出交付范围；其测试通过不代表本手册已完成新用户全流程验收。

## 当前功能范围

| 已提供 | 当前边界 |
|---|---|
| 文字导航、正文、附件、关系图、搜索 | 菜单在页内切换，保留输入；图谱来自真实链接，搜索读取已发布索引 |
| 本地 Markdown、DOCX、文字 PDF 导入 | 原件保留，暂存与知识库分开；扫描 PDF / 图片 OCR 未实现 |
| IMA 知识库、个人知识与笔记 | 手动选一篇导入和检查更新；不自动全库同步或写回 |
| 语雀单篇文档 | 需要账号具备 API 和文档读取权限；真实账号验收暂缓，可导出后本地导入 |
| Codex / DeepSeek Harness | 复用本机程序和登录；没有安装就提示，模型 API 渠道已废弃 |
| 候选提炼、旧知识对照、逐条审核 | 最多对照 3 份旧知识片段；保留要点写入资源资料卡，不自动改主题 Wiki |
| 本地保存及独立 Git 发布适配 | 网页不提交或推送；自动刷新工作流由知识私库的实例部署提供 |

钉钉接入、扫描 PDF 识别和多用户门户不在当前交付范围。推送本 **EvoKBase 应用仓库**只更新代码与手册；推送用户的**知识私库**才可能触发其已配置的索引更新，两者不能混用。
